 Rent vs Sell Analysis — PIPA-Native Module

 Context

 The user owns a low-rate home (43629 White Cap Ter) and is shopping for a second home through PIPA. The core decision is not "should I collect rent?" but "is the return on the equity trapped in the current home better
 than the guaranteed return from using that equity to avoid a 6.46% mortgage on the new home?"

 This adds a new top-level "Rent vs Sell" page to PIPA that computes four strategies (Sell Now / Keep 5Y / Keep 10Y / Rent-Then-Sell ~2029) from a single assumption set, with a strategy-aware sensitivity heatmap as a
 first-class feature. Launch is primary from the property detail page ("Analyze as Next Home") and secondary via the left nav.

 Key abstraction (non-negotiable):
 - Strategy = what the user does (sell now, keep 5Y, keep 10Y, rent-then-sell)
 - Scenario = market/financing assumptions applied to all strategies
 - Saved Run = one named assumption set + all computed strategy outputs, optionally linked to a target property

 Built PIPA-native: vanilla JS, Tailwind CDN, load()/render()/bind(), Python calc engine server-side, SQLite persistence, Chart.js via CDN.

 Assumption Model (canonical input contract)

 RentVsSellInputs is a nested dict with these top-level groups. Every field has a starter default so first-load compute works without any user entry.

 Group 1: Current Home (core)

 value_today, basis, loan_balance, mortgage_rate,

 # Monthly carrying costs split explicitly (no more PITI lump)
 monthly_principal_interest     # derived from mortgage_schedule if not entered
 monthly_taxes                  # explicit — drives tax-growth + deductibles

 monthly_hoa
 monthly_misc_owner_paid        # HOA extras, utilities, sewer/trash — user-entered

 # Rental conversion adjustments
 insurance_conversion_bump_pct  # default 0.15 — landlord policy costs more than owner-occupied
 initial_lease_up_vacancy_months # default 1.0 — vacancy before the first tenant lands

 # Core sale + rent

 land_pct, building_pct, move_out_month, rent_start_month

 Rule: monthly_piti as a single number is no longer used in any formula. The tax model reads monthly_taxes and monthly_insurance explicitly; the ownership-cost-growth paths apply to each bucket independently;
 monthly_misc_owner_paid flows into cash-flow math and grows at current_home_misc_growth_annual_pct. On rental conversion, starting monthly_insurance is multiplied by (1 + insurance_conversion_bump_pct) for every month
 the home is in rental use.

 Each path is an independent monthly_owner_cost_path so taxes and insurance can drift at different rates over the horizon.

 Group 7: Exit Friction (new — sell-now and sell-later are not the same)

 current_home_sell_cost_pct_future         # default 0.07 (may differ from _now)
 sale_prep_cost_flat                       # default 3000
 pre_sale_vacancy_months                   # default 0.5

 Group 8: Sell-Case Reinvestment (new — fairness for 10Y)

 invest_monthly_sell_savings                       # default true
 monthly_savings_reinvestment_return_annual_pct    # default 0.04
 invest_initial_sale_surplus_cash                  # default false
 surplus_cash_return_annual_pct                    # default 0.04
 The sell case has lower monthly carrying cost than the keep case. Those monthly savings, left as cash under the mattress, understate the sell case over 10 years. Modeling them as an optional reinvested stream is the
 fairness fix.

 Group 9: New-Home Drag (new)

 new_home_maintenance_pct_of_home_value_annual   # default 0.01
 Default low, but present so long-horizon comparisons are fair across strategies. Capex items (above) can also target applies_to: new_home | both.

 Group 10: Refinance (core)

 enabled, year3_rate, year5_rate, year7_rate,
 cost_pct (default 0.015), selected_path ∈ {none, year3, year5, year7}

 Group 11: Taxes (core)

 filing_status, federal_ordinary_rate, federal_ltcg_rate,
 virginia_rate, niit_enabled, niit_rate,
 section_121_mfj (default 500000), depreciation_recovery_rate (default 0.25),

 Suspended passive loss rule (simplified): at any rental year where taxable rental income is negative, the loss goes into suspended_loss_created (not current_tax_saved) because MAGI > $150k disables the $25k special
 allowance. When the property is sold in a fully taxable disposition (sell_now if already converted, or rent_then_sell), if release_suspended_losses_on_taxable_disposition is true, the accumulated suspended balance is
 released and offsets ordinary income in the year of sale — approximated as tax_benefit = suspended_loss_balance * (federal_ordinary_rate + virginia_rate). Disclaimer flag passive_loss_release_assumed is set whenever
 this fires.

 Group 12: Modeling (core)

 horizon_years (5 or 10), rent_then_sell_date (default 2029-05)

 Strategy functions

 Each takes the full RentVsSellInputs dict and horizon_months, returns a StrategyOutput:

 def compute_sell_now(inputs, horizon_months) -> StrategyOutput
 def compute_keep_rental(inputs, horizon_months) -> StrategyOutput
 def compute_rent_then_sell(inputs) -> StrategyOutput   # sell_date drives horizon

 Sell Now logic:
 - Net cash proceeds = value_today * (1 - sell_cost_pct_now) - loan_balance - sale_prep_cost_flat
 - Gain = value_today * (1 - sell_cost_pct_now) - basis; excluded under §121 MFJ up to $500k; taxable surplus at LTCG + VA + NIIT
 - New-home down payment = base_down_pct * purchase_price + net_after_tax_proceeds (→ ~53.4%, NOT hardcoded 55%)
 - New-home loan balance = purchase_price - down_payment; amortize over term; apply selected refi path
 - New-home drag: monthly maintenance (new_home_maintenance_pct_of_home_value_annual / 12 * purchase_price) + any new_home capex events + cost growth on taxes/insurance/HOA
 - Reinvestment (new): monthly carrying-cost savings vs the keep case (computed as keep-case new-home payment − sell-case new-home payment) feed through reinvestment_path(...) if invest_monthly_sell_savings is on. Any
 surplus sale cash beyond the down payment also reinvests if invest_initial_sale_surplus_cash is on.
 - Net worth at horizon = new-home equity + reinvested savings value + reinvested surplus cash value − refi costs − new-home maintenance drag − new-home capex

 Keep Rental (horizon_months = 60 or 120):
 - Current home: linear_growth_path(value_today, total_value_change_Xy, horizon_months); current mortgage continues on its own amortization schedule
 - Rent path: linear_growth_path(monthly_rent_base, total_rent_change_Xy, horizon_months)
 - Operating economics per month (new, expanded): collected_rent = gross_rent − vacancy_loss − bad_debt_loss − leasing_fee − turnover_cost, then pre_tax_cashflow = collected_rent − property_management_fee −
 routine_maintenance − explicit_capex_cash − monthly_piti − monthly_hoa − owner_cost_growth_deltas
 - Economic reserve per month = (monthly_rent_base * reserve_months_per_year) / 12, kept in a parallel stress column — NOT double-counted against explicit drag and NOT added to tax deductions
 - Annual tax calc: taxable = collected_rent - mortgage_interest - property_tax - insurance - hoa - deductible_repairs - management_fee - leasing_fee - deductible capex portion - depreciation; tax at ordinary marginal +
  VA + NIIT. Negative taxable → suspended_loss_created given >$150k MAGI phaseout (no immediate W-2 offset). Suspended losses may optionally be released at eventual sale (simplified approximation, flagged).
 - New home: base 20% down only; amortize + refi path + new-home drag (maintenance + capex + cost growth)
 - Ending net worth = current-home equity (future value × (1 − current_home_sell_cost_pct_future) − loan balance − hypothetical recapture line item) + new-home equity + cumulative after-tax rental cashflow − refi costs

 Rent Then Sell (sell_date configurable, default 2029-05):
 - Months rented = (sell_date - rent_start_month).months
 - Same operating economics as Keep Rental over those months
 - Pre-sale vacancy (pre_sale_vacancy_months) zeroes out rent collection in the final months before sale but carrying costs still apply
 - Sale: gross_proceeds = future_value × (1 − current_home_sell_cost_pct_future) × (1 − concession_pct_at_sale) − sale_prep_cost_flat; then split gain:
   - depreciation_recap_bucket = depreciation taken (mid-month convention), taxed at min(depreciation_recovery_rate, federal_ordinary_rate) + VA (not §121 excludable)
   - taxable_cap_gain_bucket = remaining gain after §121 exclusion (applies if sell_date < move_out_month + 3yr so 2-of-5 test still passes)
 - Warnings: §121 window closed (sell > move_out + 3yr); large capex within 12mo of sale; pre-sale vacancy materially changes outcome; future sell-cost > sell-now cost

 Top-line metric definitions (must match exactly):
 - trapped_equity = value_today * (1 - sell_cost_pct) - loan_balance
 - extra_new_home_loan = keep-case new-home loan − sell-case new-home loan
 - net_interest_drag_monthly = (extra_new_home_interest_month_1) - (current_home_interest_month_1) — defined at month 1 with disclaimer that it evolves over time; the drive-to-zero narrative lives in the driver bridge,
 not here
 - required_appreciation_to_breakeven_Xy = solve total_value_change_pct where keep_strategy.net_worth_end == sell_now.net_worth_end via bisection, up to ±30% bracket
 - section_121_window_status = "open" if sell_date < move_out_month + 3yr, "closing YYYY-MM" if within the next 12 months, "closed" otherwise
 - lean threshold: |delta_5y| < $25k → too_close; else winner of keep_5y vs sell_now at the default lens

 Sensitivity grid — preset-driven (not free-form in V1)

 def compute_sensitivity_grid(inputs, preset, comparator, horizon, refi_path) -> SensitivityGrid:
     # preset ∈ {
     #   "value_x_rent",            # default — current-home value vs rent change
     #   "value_x_capex",           # value change vs one-time capex shock
     #   "value_x_refi",            # value change vs refi path (Y3/Y5/Y7/none)
     #   "rent_x_vacancy",          # rent change vs vacancy/turnover drag
     #   "rent_x_reinvest_return",  # rent change vs sell-case reinvestment return
     # }
     # Each preset runs an 11x11 (or 11x4 for refi) grid, cloning inputs per cell,
     # recomputing the two strategies named by `comparator`, and returning
     # {delta, winner, magnitude} per cell plus row/column labels.

 Presets keep V1 bounded. Each grid is at most 121 cells × O(horizon_months). A full grid cold-computes in ~100–200ms. The endpoint also returns three derived breakeven metrics computed via bisection against the current
  baseline:
 breakeven_rent_change_pct
 breakeven_value_change_pct
 breakeven_capex_shock_dollars
 These are the "crossover line" numbers the heatmap ships alongside the grid.

 Prefill endpoint reads listing_data (price, HOA, taxes, insurance) and county_data (assessed value, tax history) and returns a partial NewHomeInputs dict + a source_prefill_version string so saved runs can track where
 their numbers came from.

 Sensitivity caching: the endpoint computes sha1(json.dumps({subset_of_assumptions, horizon, refi_path, comparator, metric}, sort_keys=True)) and uses it as a key in an in-memory LRU (maxsize=64). Cache lives on the app
  state, not per-request. Cold computes take ~100–200ms for an 11×11 grid; cache hits are free. The LRU is fine for single-user PIPA; no Redis needed.

 Save-time snapshotting: POST /runs and PUT /runs/{id} both snapshot:
 - target_property_snapshot_json — from the referenced property's current listing data (price, HOA, taxes, assessed value)
 - current_home_snapshot_json — from the referenced current-home profile's config_json
 - source_prefill_version — from the prefill response if the inputs came from one

 Stale recomputation: GET /runs/{id} checks stored.calc_version != CALC_VERSION. If mismatched, recompute → update in place → return with recomputed: true.

 Compute behavior (critical):
 - /calculate runs on input changes with 300ms debounce — cheap (<50ms server-side)
 - /sensitivity does NOT run on input edits. It runs only when:
   a. user clicks "Refresh Heatmap"
   b. user changes a heatmap control (horizon / refi / comparator / metric)
   c. user stops editing inputs for 1500ms AND the heatmap panel is visible AND a cached hash doesn't already match
 - The heatmap shows a "⚠ Stale — refresh to update" banner when inputs have changed since the last computed grid
 - Frontend caches results in-memory keyed by request hash; Refresh Heatmap force-bypasses cache

 State management: module-local _state = { inputs, outputs, savedRuns, activeLens, heatmapCache, heatmapStale }. On load, reads query params (new_home_property_id, run_id), fetches prefill or saved run, seeds inputs,
 triggers first /calculate. Heatmap is NOT auto-fetched on page load — the panel shows a "Load heatmap" button until clicked.

 Section-level buttons inside collapsible card headers use event.stopPropagation() to match existing PIPA collapsible behavior.

 Warning badges

 Render amber/red badges on specific cards when:
 - Sell proceeds are negative or tiny
 - Rental cashflow negative (before or after tax)
 - §121 exclusion window closing within the horizon
 - Depreciation recapture > $20k at horizon
 - Rent-then-sell date past §121 favorable window
 - Suspended passive losses accruing (not offsetting W-2 immediately)
 - High capex concentration in first 24 months (> $20k)
 - Multiple large capex events (>2) within 12 months of a planned sale
 - High vacancy + turnover combination making rent-growth assumptions misleading
 - New-home maintenance omitted entirely in 10Y mode (flag if new_home_maintenance_pct == 0)
 - Sell-case reinvestment disabled in 10Y mode (flag the fairness gap)
 - Future sale friction materially larger than sell-now friction (sell_cost_pct_future > sell_cost_pct_now + 1pp)

 Design Rules (non-negotiable)

 1. One assumption set → all four strategies. Strategies are rows in the output; scenarios are named assumption sets.
 2. Sell case uses base down % + net sale proceeds, never hardcoded 55%. Must land near 53.4% with defaults.
 3. Growth inputs are total horizon changes (−10% to +10%), spread linearly over months. Not annual CAGR.
 4. Economic reserve ≠ tax deductions. Parallel tracks. Reserve for stress-testing; tax model uses actual deductible expenses + depreciation.
 5. Section 121 with depreciation-recapture explicit. Recapture bucket (25% max rate) shown as its own line.
 6. Planning math, not tax advice. Disclaimer visible on the page.
 7. Calculations live in Python. JS only collects, requests, renders.
 8. Property-detail launch is primary. Standalone nav entry is secondary but supported.
 9. assumptions_json is the source of truth. outputs_json is a cached snapshot, recomputed when calc_version changes.
 10. Heatmap is user-triggered, never auto-recomputed on keystrokes. Stale banner communicates when the grid no longer matches the inputs.
 11. Compare runs is a dedicated page, not a drawer feature.
 12. Save-time snapshots freeze provenance — listing data refreshes don't silently change what an old run "means."
 13. Landlord drag is modeled explicitly, not hidden inside a single reserve number. Vacancy, bad debt, leasing, turnover, management, routine maintenance, and explicit capex each have their own line in the operating
 model and their own bucket in the driver bridge.
 14. Sell-case reinvestment is first-class, not an afterthought. Otherwise the sell case is silently penalized in long horizons.
 15. Exit friction is separate for sell-now vs sell-later. Sell-cost %, sale prep cost, pre-sale vacancy, and concessions can differ between the two paths.
